# Data Inspection Report (SPEC §3.2)

Generated by [`scripts/inspect_data.py`](scripts/inspect_data.py) (`python scripts/inspect_data.py` or `make inspect`). Full console output and plots are written to `outputs/inspection/`. This report records the findings and the preprocessing decisions that follow from them.

> **Layout note:** the dataset lives under `data/` in two stages: `data/data_org/` (original, untouched — `images_RGBA/`, `labels_org/`) and `data/data_convert/` (derived — `images_RGB/`, `labels_bin_128/`, built from `data_org/` by [`scripts/build_data_convert.py`](scripts/build_data_convert.py) / `make data-convert`). Inspection (this report, `scripts/inspect_data.py`) always analyzes `data_org/`; the training pipeline (`roof_seg/dataset.py`) always reads `data_convert/` — see §4/§5 for why.

## 1. File inventory

- Originally 30 images and 25 labels, matching SPEC §2. After excluding `278`'s label (see §3), the active dataset is **30 images in `data/data_org/images_RGBA/`, 24 labels in `data/data_org/labels_org/`**.
- No orphan labels (every label has a matching image).
- The 6 images without a label are the configured test set: `278`, `535`, `537`, `539`, `551`, `553`.

## 2. Dimensions

All 30 images are 256×256 `RGBA`; all 24 labels are 256×256 grayscale (`L`). No shape or mode mismatches.

## 3. Duplicate / inconsistent labels — `278`'s label is wrong

`270` and `278`'s label files were **byte-identical**, but their satellite images are visually completely different (different roof colors, layout, and surroundings — confirmed in `outputs/inspection/alignment_grid.png`/`outputs/inspection/test_set_preview.png` and by RGB channel means). On inspection it is unambiguous that `278`'s label does **not** correspond to `278`'s image at all — it is `270`'s label, almost certainly copy-pasted onto `278` during annotation. This is a clear labeling mistake, not a legitimate duplicate scene.

**Decision:** training on a wrong label would actively teach the model an incorrect image→mask mapping and degrade prediction quality, so `278`'s label (`data/data_org/labels_org/278.png`) has been **deleted** rather than kept — it never existed in `data_org/` to begin with in the current layout. Its image is not discarded, though — `278` has been added to `TEST_IDS` in `roof_seg/config.py`, so it is treated as a sixth test image and still gets a prediction once the model is trained (no ground truth is needed for the test set anyway). This drops the effective **training** set from 25 to **24** labeled pairs, and grows the **test** set from 5 to **6** images. See the file-inventory check and the duplicate-label note in `scripts/inspect_data.py`, which now expect 30 images / 24 labels / `TEST_IDS = (278, 535, 537, 539, 551, 553)`.

## 4. Alpha channel audit

24 of the 30 images (80%) contain non-opaque pixels (`alpha < 255`); opacity ranges from **73.9%** (`532`) to **100%** (6 images: `121`, `272`, `274`, `284`, `314`, `417`). All 6 test images (including `278`, 98.7% opaque) have some non-opaque pixels (opacity 84.5%–98.7%).

Visual inspection (`outputs/inspection/alignment_grid.png`, `outputs/inspection/test_set_preview.png`) shows this is **not** antialiasing at tile borders — it's rectangular **black censorship boxes** overlaid on the imagery (redacting neighboring buildings/addresses) plus a small "Google / imagery attribution" watermark strip in the bottom-left corner. The masked pixels are RGB ≈ (5, 5, 4), i.e. already rendered black; the alpha channel is low there too but doesn't reveal anything the RGB doesn't already show.

Critically, these masked regions almost never coincide with roof labels: across the 24 active training pairs, only 2 images have *any* overlap between `alpha<255` regions and `label>0` roof pixels, and both are small (`315`: 1.2%, `320`: 0.6% of that image's roof pixels). No test image's roof-relevant area is meaningfully affected either (censorship boxes sit over unrelated neighboring lots, not the target houses).

**Decision:** drop the alpha channel and train on RGB only. The masked regions are already near-black in RGB, so the model sees them as "dark unremarkable area" whether or not alpha is used — no separate handling (e.g. an ignore-mask) is needed given the negligible roof overlap.

This decision is materialized as an actual dataset, not just a load-time transform: [`scripts/build_data_convert.py`](scripts/build_data_convert.py) (`make data-convert`) writes an RGB-only copy of every image to `data/data_convert/images_RGB/`. The original RGBA dataset in `data/data_org/images_RGBA/` is left untouched, and the training pipeline (`roof_seg/dataset.py`) reads only from `data_convert/`.

## 5. Label value distribution & binarization rule

Aggregated over the 24 active labels: 1,321,236 background px (`0`), 187,452 roof-interior px (`255`), 64,176 boundary px (`1`–`254`, **4.08%** of all pixels). The histogram (`outputs/inspection/label_value_histogram.png`) is strongly bimodal at 0 and 255, with a thin, roughly uniform spread of boundary values in between (antialiasing on polygon edges) — no secondary cluster that would suggest a different label convention.

Comparing binarization rules per image:

| Threshold | Mean roof area | Range |
|---|---|---|
| `label > 0` | 16.00% | 6.09% – 31.48% |
| `label >= 128` | 14.00% | 5.32% – 27.71% |

`> 0` includes on average 1.99 percentage points more roof area than `>= 128` (max difference 3.76pp on image `270`), because it counts all boundary pixels as roof instead of only the darker half of them.

**Decision (revised): use `mask = 255 * (label > 128)`.** Both thresholds are defensible — `>0` is an "any-coverage" rule (a pixel counts as roof if the annotated polygon touches it at all, preserving the full footprint including faint edges); `>128` is a "majority-coverage" rule (a pixel counts as roof only if more than half its area is covered, i.e. roof is the *more likely* label for that pixel). The project initially defaulted to `>0` per the SPEC's stated canonical rule, but settled on **`>128`** as the final choice: it's the more standard interpretation of "binarize a soft/antialiased mask" (round to the nearest class rather than round up), and it's the threshold actually used for the consolidated `data/data_convert/` dataset the pipeline reads from. The practical difference is small — per §5's comparison above, `>128` yields a consistently tighter mask, roughly 2 percentage points less roof area on average (max 3.76pp on the most affected image), concentrated entirely in the ~4% of pixels that were ambiguous (antialiased boundary) to begin with. Class balance (§6) and downstream metrics are essentially unaffected either way.

The antialiased `1`–`254` boundary values (see §3's discussion) come from rasterizing vector roof polygons — a generic rendering default, not something done for this ML task — and would need scaling/clamping to be usable as a hard BCE/Dice target regardless. This decision is materialized as an actual dataset via [`scripts/build_data_convert.py`](scripts/build_data_convert.py) (`make data-convert`), which writes strictly-`{0,255}`-valued labels to `data/data_convert/labels_bin_128/` (the standard binary-mask convention — a raw `{0,1}` PNG would be indistinguishable from solid black in any viewer, since 1/255 is imperceptible) and renders `outputs/inspection/data_convert_comparison.png` — org image | convert image | org label | convert label — for a handful of samples. The original `data/data_org/labels_org/` is left untouched, and the training pipeline reads only from `data_convert/`.

## 6. Class balance

Roof foreground ratio (`label > 128`, the final rule — see §5) per training image ranges from **5.31%** (`274`) to **27.71%** (`270`, the sole highest outlier after `278` was dropped), mean 14.00%, std 4.42%. (With the earlier `label > 0` rule these were 6.09%–31.48%, mean 16.00% — see §5 for the comparison.) Background dominates every image, confirming the class imbalance noted in the SPEC.

**Decision:** use a loss that handles imbalance — BCE + Dice (SPEC default) — rather than plain BCE, and do not rely on pixel accuracy as an evaluation metric.

## 7. Image/label alignment

`outputs/inspection/alignment_grid.png` shows image | label | overlay for 6 randomly sampled training pairs (`241`, `303`, `317`, `324`, `379`, `417`). Roof polygons align tightly with the visible roof outlines in every sample — no offset, flip, or scale mismatch.

## 8. Test-set inspection

All 6 test images (`278`, `535`, `537`, `539`, `551`, `553`) are 256×256 RGBA, same format as training images. `535` and `537` each have a black censorship box; none of the 6 show anything structurally different from the training images (no missing roofs, no unusual color casts). `278` itself looks like an ordinary, unremarkable satellite tile — nothing about the image explains why its label was wrong; the mistake was purely in annotation. `outputs/inspection/test_set_preview.png` has thumbnails with opacity annotated.

## Summary of decisions carried into §3.3

| Decision | Choice | Rationale |
|---|---|---|
| Model input channels | RGB (drop alpha); materialized at `data/data_convert/images_RGB/` via `scripts/build_data_convert.py` (`make data-convert`) | Alpha only flags already-black censorship boxes; negligible overlap with roof pixels |
| Label binarization | `mask = 255 * (label > 128)`; materialized at `data/data_convert/labels_bin_128/` via the same script | Revised from an earlier `label > 0` default — see §5. Majority-coverage rule; ~2pp tighter mask, concentrated in the ~4% antialiased boundary |
| Wrong label (`278`) | **Label deleted, image moved to `TEST_IDS`** | `278`'s label was `270`'s (copy/paste error); training on it would teach a wrong mapping. Kept the image so it still gets a prediction |
| Loss function | BCE + Dice | Roof coverage 5–28% of frame — background-dominated, imbalance-sensitive |
| Test-set membership | `TEST_IDS` in `roof_seg/config.py` (now 6 IDs) | Confirmed to match the 6 images with no label file |
| Training pipeline input | `roof_seg/dataset.py` reads `data/data_convert/` only, never `data/data_org/` | Keeps preprocessing (alpha-drop, binarization) a fixed, materialized artifact rather than recomputed per run |
